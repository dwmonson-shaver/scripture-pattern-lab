## Per-Finding Rationale

### D-CLOSE-001

Observed evidence: canonical-09 documents `def retrieve(plan: QueryPlan, *, contextualize: bool = False) -> RetrievalResult` at `docs/canonical/09_backend-service-boundaries.md:150`, but the shipped implementation requires `plan`, `scope`, and `engine`, with optional `contextualize` and `registry`, at `src/retrieval/retrieve.py:30`. The contextualization interface block similarly shows `registry: ConceptRegistry` as required at `docs/canonical/09_backend-service-boundaries.md:191`, while implementation accepts `registry: ConceptRegistry | None = None` at `src/retrieval/contextualization.py:199`.

Why it matters: this is not a runtime bug in the current CLI path, but it weakens slice-level coherence. A future caller implementing against canonical-09 would call the wrong `retrieve()` shape and fail before execution, and the registry optionality is part of the shared lemma/concept contract because lemma-only queries do not need a registry.

Suggested fix: update the canonical interface blocks to match the actual MVP dependency-injected signatures, or intentionally wrap the implementation behind a simpler public interface if canonical is meant to hide engine/scope injection.

### D-CLOSE-002

Observed evidence: canonical-09 says the `N >= 5` fallback is "identity + reverse + N pairwise swaps" at `docs/canonical/09_backend-service-boundaries.md:223`. The implementation builds identity, reverse, and adjacent swaps for `range(n - 1)` at `src/retrieval/contextualization.py:181`, and tests pin `N=5` as six permutations: identity, reverse, and four adjacent swaps at `tests/unit/test_contextualization.py:252`.

Why it matters: the implementation is deterministic, bounded, and matches the performance target noted for validator max `N=10` (11 engine re-entries). The remaining issue is canonical ambiguity: "N pairwise swaps" reads as one more swap than code produces, and does not say adjacent.

Suggested fix: change canonical-09 to "identity + reverse + `N-1` adjacent pairwise swaps, truncated at 24" so the spec, tests, and CLI counts all describe the same subset.

### D-CLOSE-003

Observed evidence: `_print_contextualization()` joins every resolved lemma into a single string and prints it directly at `scripts/query.py:148`, then prints every `sequence_label` directly at `scripts/query.py:168`. Those values are sourced from arbitrary registry lemma lists and node values, with labels generated by joining step values in `src/retrieval/contextualization.py:189`.

Why it matters: the CLI is the only user-facing consumer in this slice. For the current seed concepts the output is readable, but a broader concept mapping or long lemma/value names can produce very wide lines, making the baselines and alternative-ordering table hard to scan. This is quality-of-life rather than a correctness blocker.

Suggested fix: cap or wrap the resolved-lemma display (for example first 5 lemmas plus "+N more") and apply a max-width truncation/wrapping policy to `sequence_label` while preserving full data in the `RetrievalResult`.
